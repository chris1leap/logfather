PikPak Fleet Database Plan

Replacing the spreadsheets with one company database in Azure that holds the fleet, its customers, SKUs, trays, maintenance, issues and root causes, what was packed each day, and the telemetry (temperatures, currents) in the same database; trackable to the row, and backs itself up.

How the system works

Three layers, each replaceable on its own.

  1. One database, the source of truth. Azure Database for PostgreSQL holds every record: the relational tables, JSON where a record is naturally a document (a SKU's recipe, a run's counters), and the time series through the TimescaleDB extension. Spreadsheets become read-only views of it, never the other way round.
  2. One entry app. A small internal web app for adding and editing records, with sign-in through the company Microsoft account, roles, and a full change history on every row. Phase one is a generated admin interface, not bespoke screens.
  3. Consumers. Excel and Power BI read from views with a read-only login. Grafana reads the telemetry tables directly. The Logfather reads customers, lines, systems and SKUs from the database instead of its settings file, writes what each system packed each day into it, and can raise an issue from the Errors / Stops window with the system and day filled in.

What "trackable" means here. Every table carries who created and last changed a row and when, and the entry app writes a history row for every change on the core tables, so "what did this system's line assignment look like on 3 March" is a single query. Nothing is ever hard-deleted; rows are retired with an end date.

What "easy to back up" means here. The managed service takes automatic backups with point-in-time restore for up to 35 days, optionally copied to a second region. For years-long retention a weekly logical dump goes to Blob Storage with a lifecycle rule, which is one small scheduled job. A restore drill is a ticket, not an afterthought.

The engine

Decided: Azure Database for PostgreSQL Flexible Server, with the TimescaleDB extension, one database for everything.

Relational tables for the fleet, JSONB columns where a record is naturally a document, and TimescaleDB hypertables for the telemetry, all under one backup, one sign-in and one connection string. Django speaks PostgreSQL natively, Grafana has a first-class PostgreSQL data source, and Excel and Power BI connect through the PostgreSQL connector.

What we give up against Azure SQL: built-in temporal tables (row history comes from the app layer instead), the Excel "SQL Server" connector everyone has seen before (the PostgreSQL one needs a one-time driver install), and built-in long-term backup retention (a weekly dump job covers it). What we gain: no second store for telemetry, no cross-store joins, no KQL, and a smaller bill.

Not recommended: Dataverse or SharePoint lists (licensing per user, weak relational model, hard to query from outside), a separate NoSQL store (this is relational data with many-to-one links everywhere), or a separate time-series service now that Timescale lives inside the same database.

Keys and conventions

  • Surrogate primary keys everywhere: <table>_id, bigint generated always as identity. Serial numbers, tray numbers and SKU codes are human identifiers that get retyped, reissued and occasionally corrected, so they must not be what foreign keys point at.
  • Natural keys as unique constraints: system.serial_number (with display_name "PikPak 007" unique too, but only ever a label), tray.unique_number, sku.code, (package_id, software_release.git_commit). Duplicates are rejected at the database, not by convention.
  • Human references on things people talk about: ISS-0001, MNT-0001, RC-0001, generated from the id and shown everywhere. They are labels, not keys.
  • History as date ranges, not overwrites. Where a system is, which component is fitted, which software runs: each is a row with from and to dates. The current state is the row whose to is null, and only one such row is allowed per subject (partial unique index).
  • Lookups are tables, not free text. Statuses, severities, event types, component types and issue categories are small tables, so a report can group by them and a new value is a row, not a code change.
  • Audit columns on every table: created_at, created_by, updated_at, updated_by; plus a history table per core entity written by the app on every change (django-simple-history), giving the same "as of" queries a temporal table would.
  • Time series are hypertables. Wide rows keyed by time, system and component, partitioned by time automatically, compressed after 30 days, kept for years.
  • Names: singular snake_case table names, UTC timestamps (timestamptz), a notes column where people will inevitably want one.

Products and trays

No separate tray-type table: most trays are unique with subtle differences, so a shared design record would be one row per tray anyway. A SKU points at the tray it is packed in. No recipe-version table either: a SKU never changes once defined and is the same for every customer that packs it, so the SKU row is the whole definition and the code alone identifies it.

traytray_idunique_numberEach tray is its own design with subtle differences, so the design lives on the tray itself: dimensions, cavity layout, material, supplier, drawing reference; plus customer_id, site_id, status (in service, damaged, retired), commissioned_on, retired_on. A damaged tray is not a separate log: it is an issue with the tray linked, and the root cause says why.

Production

What was actually packed. Nobody types this: the Logfather already reads runs, SKUs and the pick-and-place counters from Elastic and writes them here nightly, so the database can answer "how many of SKU X did PikPak 012 pack last Tuesday, and in which tray" without a query against Elastic.

TablePrimary keyUnique / natural keyColumns worth naming
production_runrun_idelastic_run_idsystem_id, sku_id, tray_id (from the SKU's tray unless overridden), started_at, ended_at, products_packed, trays_packed, products_seen, products_rejected, pick_movements, counters (jsonb, the raw Pick-n-place update), source (Elastic / manual). One row per run as the behaviour node starts and stops it (Argus 2 has run ids; Argus 1 runs are cut at SKU changes).
production_dayproduction_day_id(system_id, day, sku_id, tray_id)The daily roll-up of the runs: products_packed, trays_packed, products_rejected, pick_movements, run_count, minutes_running, minutes_on. This is the table reports and Excel use; runs are the detail behind it.

Telemetry

Raw readings and their daily summary live in the same database as everything else, joined to the fleet tables by plain foreign keys. The raw table is a TimescaleDB hypertable: it looks like an ordinary table but is partitioned by time behind the scenes, compresses chunks older than 30 days, and drops chunks past the retention we set.

TableKeyColumns worth naming
telemetry(time, system_id, position, metric)time (timestamptz), system_id, position ("servo 2", "brake resistor", "PSU 48V"), metric (temperature, current, voltage, pressure, vacuum), value (double), unit, source (Grafana backend, Elastic, robot). Hypertable on time; compression after 30 days; retention 5 years. Indexed on (system_id, position, metric, time desc) so a Grafana panel for one servo is instant.
telemetry_day(system_id, position, metric, day)system_component_id (the fitting in place that day), min_value, avg_value, max_value, minutes_above_threshold, threshold_used, sample_count. A Timescale continuous aggregate refreshed nightly; the table issues and maintenance planning read.
telemetry_threshold(component_type_id, metric)warning and alarm levels per component type and metric, so "minutes above threshold" changes with a row edit, not a code change.

Lookups

Each is (id, code, label, sort_order, active): system_status, component_status, tray_status, event_type, issue_category (shared by root causes), issue_severity, organisation_kind.

Views for Excel, Power BI and Grafana

  • v_fleet_current: every system with its customer, site, line and status today.
  • v_site_contacts: each site's contacts with role, phone and email, primary first.
  • v_system_components_current: what is fitted where, with serial numbers.
  • v_maintenance_log: events with system, customer, type, downtime, technician.
  • v_issue_register: issues with their root cause and linked maintenance.
  • v_software_current: the release each system runs per package, with approved flag.
  • v_production_day: per system per day per SKU, with customer, line and tray names, ready for a pivot table.
  • v_telemetry_day: per component per day per metric, with the component serial and its system's customer and line.
  • v_telemetry_labelled: raw readings joined to display_name, customer and the fitted component; the view Grafana dashboards select from.

DDL sketch

The shape of the core, to make the conventions concrete. The full migration set is a ticket.

CREATE TABLE system (
  system_id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  serial_number text NOT NULL UNIQUE,     -- 35-2300-007, the identity
  display_name  text NOT NULL UNIQUE,     -- PikPak 007, what people see
  folder_name   text NOT NULL UNIQUE,     -- PikPak007, the CCTV share folder
  generation    text NOT NULL,            -- Argus 1 / Argus 2
  status_id     int  NOT NULL REFERENCES system_status(status_id),
  build_date    date,
  notes         text,
  created_at timestamptz NOT NULL DEFAULT now(), created_by text NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now(), updated_by text NOT NULL
);
-- row history: one table per core entity, written by the app on every change

CREATE TABLE system_deployment (
  deployment_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  system_id     bigint NOT NULL REFERENCES system(system_id),
  line_id       bigint NOT NULL REFERENCES production_line(line_id),
  installed_on  date NOT NULL,
  removed_on    date,
  reason        text
);
-- only one current placement per system
CREATE UNIQUE INDEX ux_deployment_current ON system_deployment(system_id) WHERE removed_on IS NULL;

CREATE TABLE root_cause (
  root_cause_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  reference     text GENERATED ALWAYS AS ('RC-' || lpad(root_cause_id::text, 4, '0')) STORED UNIQUE,
  name          text NOT NULL UNIQUE,
  description   text,
  category_id   int NOT NULL REFERENCES issue_category(category_id),
  active        boolean NOT NULL DEFAULT true
);

CREATE TABLE issue (
  issue_id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  reference     text GENERATED ALWAYS AS ('ISS-' || lpad(issue_id::text, 4, '0')) STORED UNIQUE,
  system_id     bigint REFERENCES system(system_id),
  tray_id       bigint REFERENCES tray(tray_id),          -- a damaged tray is an issue
  site_id       bigint NOT NULL REFERENCES site(site_id),
  reported_at   timestamptz NOT NULL,
  reported_by   bigint NOT NULL REFERENCES person(person_id),
  title         text NOT NULL,
  description   text,
  severity_id   int NOT NULL REFERENCES issue_severity(severity_id),
  root_cause_id bigint REFERENCES root_cause(root_cause_id),  -- null until known
  grafana_url   text,
  jira_key      text,
  notes         text
);

-- telemetry: an ordinary table turned into a hypertable
CREATE EXTENSION IF NOT EXISTS timescaledb;
CREATE TABLE telemetry (
  time      timestamptz NOT NULL,
  system_id bigint NOT NULL REFERENCES system(system_id),
  position  text NOT NULL,       -- servo 2, brake resistor, PSU 48V
  metric    text NOT NULL,       -- temperature, current, voltage, pressure, vacuum
  value     double precision NOT NULL,
  unit      text,
  source    text
);
SELECT create_hypertable('telemetry', 'time');
CREATE INDEX ON telemetry (system_id, position, metric, time DESC);
ALTER TABLE telemetry SET (timescaledb.compress, timescaledb.compress_segmentby = 'system_id, position, metric');
SELECT add_compression_policy('telemetry', INTERVAL '30 days');
SELECT add_retention_policy('telemetry', INTERVAL '5 years');

  ('35-2300-006', 'PikPak 006', 'PikPak006', 'Argus 2'),
  ('35-2300-007', 'PikPak 007', 'PikPak007', 'Argus 2'),
  ('35-2300-010', 'PikPak 010', 'PikPak010', 'Argus 1'),

INSERT INTO system_deployment (system_id, customer, line_name, installed_on)
SELECT system_id, 'EVG', 'Line 6', '2026-03-24' FROM system WHERE serial_number = '35-2300-006';

-- The fleet as it stands
SELECT s.serial_number, s.display_name, s.generation, d.customer, d.line_name, d.installed_on
FROM system s LEFT JOIN system_deployment d ON d.system_id = s.system_id AND d.removed_on IS NULL
ORDER BY s.serial_number;

-- Telemetry: a hypertable with an hour of fake servo temperatures
CREATE TABLE telemetry (
  time timestamptz NOT NULL, system_id bigint NOT NULL REFERENCES system(system_id),
  position text NOT NULL, metric text NOT NULL, value double precision NOT NULL, unit text
);
SELECT create_hypertable('telemetry', 'time');
INSERT INTO telemetry
SELECT now() - (n || ' seconds')::interval, s.system_id, 'servo 2', 'temperature', 40 + 5 * sin(n / 300.0), 'C'
FROM generate_series(0, 3600, 10) n, system s WHERE s.serial_number = '35-2300-007';

-- Five-minute maxima, the shape of the daily summary
SELECT time_bucket('5 minutes', time) AS bucket, max(value) AS max_c
FROM telemetry GROUP BY bucket ORDER BY bucket DESC LIMIT 6;

-- A second current placement for the same system is refused
INSERT INTO system_deployment (system_id, customer, line_name, installed_on)
SELECT system_id, 'EVG', 'Line 7', '2026-09-07' FROM system WHERE serial_number = '35-2300-006';

Everything together stays around £100 a month, which is the budget alert in DB-013. The largest cost is people, not Azure.

Order of value. After Epic 2 and the fleet part of Epic 3, the database already answers the questions the spreadsheets cannot: where each system is and was, what is fitted in it, and what it runs. Issues and the root cause catalogue (DB-026, DB-044) are the next most valuable and the most used day to day. Production and telemetry follow, fed by jobs rather than typing.

Risks. Spreadsheet data that does not reconcile (DB-032 exists for this). Two sources of truth during the parallel run (freeze the spreadsheets). Entra group management landing with nobody (name an owner in DB-002). Telemetry volume outgrowing the burstable tier (watch CPU in DB-071; the step up is a portal change, not a migration). The temptation to build bespoke screens before the generated admin has been used for a month (resist it).
